# v0.1.6 Autonomous Controller and Runtime Upgrade

## Decision

Fleet uses a four-layer control hierarchy:

1. The human directs Claude Code.
2. Claude Code is the controller and contract issuer.
3. Fleet deterministically enforces the admitted contract and owns lifecycle state.
4. Codex lanes execute bounded work on Fleet-owned threads.

Fleet must not ask the human for redundant approval when the original admitted contract already
authorizes the work. It returns real scope, authority, external-effect, or user-choice questions to
Claude Code. Claude answers from the existing user context when possible and asks the human only
when new authority is actually required.

## Confirmed root cause for stale console behavior

The user plugin cache contains Fleet 0.1.5, but the installed Ctrl+G integration ownership record
still points to an immutable 0.1.0 runtime copy. The launcher therefore opens old TUI code even
after a marketplace update. This explains the old `ENTER DETAIL` footer, missing embedded Codex
session, and static COMPLETE posture.

Plugin installation and integration-runtime installation are separate versioned surfaces. A Fleet
release is not live until both match. Setup must support a fail-closed upgrade of Fleet-owned runtime
files without overwriting user-owned editor settings.

## Runtime outcome protocol

Every Codex turn receives the admitted prompt plus a Fleet-owned execution envelope. The envelope
states that the contract already authorizes execution within its declared authority, requires work
and verification in the current turn, and forbids asking for redundant approval.

`turn/start.outputSchema` requires a structured result with these fields:

- `outcome`: `accomplished`, `continue_within_authority`, `needs_controller`, or `blocked`.
- `summary`: bounded operator-facing result.
- `workPerformed`: bounded list of concrete actions completed.
- `evidenceRefs`: bounded references supporting the claim.
- `artifactRefs`: bounded workspace-relative artifacts produced or inspected.
- `verification`: bounded list of checks actually performed.
- `controllerRequest`: null or a structured request with a reason kind and bounded question.
- `stopReason`: null or a bounded reason for stopping.

`complete` remains a worker claim, not independent verification. Fleet accepts that claim only when
the structured outcome is `accomplished`. A missing or malformed result is incomplete, not success.

## Autonomous recovery state machine

- `accomplished`: persist evidence metadata and finish as `complete`.
- `continue_within_authority`: start another turn on the same Codex thread with the same model,
  effort, workspace, and authority. Never create a replacement lane.
- `needs_controller` with `redundant_approval`: treat it as recoverable within authority.
- `needs_controller` for new authority, external effect, missing input, or genuine user choice:
  finish as `blocked` with phase `needs-controller` and return the exact bounded question to Claude.
- `blocked`: finish as `blocked` and preserve the reason.
- Missing/malformed structured output: one bounded repair continuation, subject to the same total
  automatic-continuation budget.
- Maximum automatic continuations: two. Exhaustion finishes as `blocked` with phase
  `needs-controller`; it never fabricates completion.

Automatic continuation is forbidden when it would change workspace, lane ID, thread, model,
effort, authority, network/browser/image permission, checkout, or external-effect grants. An
unknown external outcome remains `outcome_unknown` and is never blindly retried.

## Operator experience

The console shows the loaded Fleet version so stale runtime is immediately visible. During internal
recovery a lane remains active and displays `RECOVERING n/2`. A genuine controller request displays
`BLOCKED / CLAUDE ACTION` with the bounded question. Enter opens the real app-server transcript;
messages go to the active turn with steering or continue the same terminal thread. Ctrl+G returns to
the Fleet dashboard, while q/Esc returns control to Claude Code.

KITE uses a visible but bounded four-frame animation at four frames per second for queued, running,
recovering, and complete-awaiting-verification states. Pausing motion freezes the formation and says
so explicitly. Reduced-motion configuration remains authoritative and the console must not claim
that motion resumed when the environment forbids it.

## Integration upgrade safety

An upgrade is allowed only when the ownership manifest, launcher hash, runtime hash, settings path,
and Fleet-written editor values still match the prior Fleet-owned installation. The upgrade stages a
new versioned runtime, verifies it, atomically replaces the launcher, and then updates ownership.
Mismatch stops without overwriting anything. Original pre-Fleet editor values remain unchanged so a
later uninstall can restore them.

## Capability boundary

GPT Image remains a callable Fleet lane capability when its smoke test passes; produced images must
be saved inside the admitted workspace and opened by Claude Code before presentation. Desktop-only
Browser, Chrome Control, and Computer Use are not advertised to CLI lanes unless capability preflight
finds a callable tool. Missing capabilities are reported to Claude Code rather than imitated.

## Release acceptance

The release requires RED/GREEN regression evidence for setup upgrade, real PTY Enter/session,
visible/pauseable motion, structured outcome parsing, automatic same-thread recovery, controller
handoff, terminal immutability, and skill/template behavior. It then requires the full test suite,
plugin validation, security/license/performance/docs checks, package verification, a local live
integration upgrade, source/cache comparison, commit, push, marketplace update, and a new Claude
Code session for pickup.
