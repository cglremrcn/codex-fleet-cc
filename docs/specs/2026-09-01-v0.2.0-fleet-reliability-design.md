# Fleet v0.2.0 Reliability and Orchestration Design

## Verdict

Fleet v0.2.0 turns valid Codex work into durable, actionable controller state. Claude Code remains
the controller, Fleet remains the deterministic authority and lifecycle boundary, and Codex lanes
remain bounded workers. The release fixes every field-proven Fleet defect in the August 29–31 field
report, while platform limitations receive measured, explicit handoffs instead of fabricated success.

## Success criteria

The release is successful when all of the following are true:

- A valid `needs_controller` or `blocked` result is never converted to `outcome_unknown` merely
  because it omitted artifacts, verification, a controller request, or a stop reason that its
  outcome does not semantically require.
- A valid `accomplished` result becomes `complete` only with concrete work, evidence, and
  verification. Optional empty artifact lists do not block completion.
- A malformed result names missing, unknown, and invalid fields without persisting secrets or raw
  reasoning. Mutable work remains fail-closed when its effects cannot be reconciled.
- A timed-out `start` response cannot encourage a blind retry. Fleet reconciles the exact admitted
  lane identities from durable state and either returns recovered admission evidence or an explicit
  uncertain-admission response that says not to redispatch.
- Supervisor restart evidence is represented as `interrupted`, not ordinary worker failure. Fleet
  preserves the prior thread, turn, last message, work/evidence metadata, and reconciliation need.
- `authority.network = "live"` reaches Codex app-server as `sandboxPolicy.networkAccess = true`;
  `network = "off"` reaches it as `false`. Read-only and workspace-write boundaries remain intact.
- Large workspaces keep active and attention-requiring lanes discoverable in CLI and TUI surfaces.
  TUI selection always remains inside a visible viewport.
- Local marketplace cache, installed Ctrl+G runtime, source manifests, release archive, and GitHub
  Release all report the same version.

## 1. Structured outcome contract

The output schema keeps `additionalProperties: false`, but required fields are separated from
conditional fields. `outcome`, `summary`, `workPerformed`, and `evidenceRefs` are structurally
required. `artifactRefs` and `verification` normalize to empty arrays; `controllerRequest` and
`stopReason` normalize to null when omitted.

Semantic validation remains strict:

- `accomplished` requires non-empty `workPerformed`, `evidenceRefs`, and `verification` before Fleet
  may emit `complete`.
- `needs_controller` requires a structured `controllerRequest`.
- `blocked` requires a non-empty `stopReason` or a structured controller request.
- `continue_within_authority` may omit verification and artifacts, but mutable partial activity is
  not automatically replayed.
- Unknown fields remain rejected so misspelled evidence fields cannot disappear silently.

Parser errors return a bounded diagnostic containing exact `missing`, `unknown`, and `invalid`
field names. Fleet preserves its already-sanitized `lastMessage` and stores bounded structured
diagnostics; it does not add raw model output, prompts, reasoning, secrets, cookies, or credentials
to durable state.

The schema gains optional `commitRefs` and `configChanges` arrays. A lane must not create commits in
Fleet's restricted workspace flow; the normal value is an empty `commitRefs`. If a lane nevertheless
claims a commit, Fleet verifies each hexadecimal SHA with read-only Git plumbing in the admitted
repository. An unresolvable SHA turns the result into `needs_controller` with a precise diagnostic,
never `complete`. `configChanges` lists project-relative configuration paths changed by the lane and
is shown separately in result/evidence output. Fleet displays a commit as verified evidence only
when it resolves in the admitted repository; commit-like prose in a summary is never promoted to a
commit fact.

## 2. Admission and timeout reconciliation

Supervisor requests gain a typed timeout error recording whether the request bytes were sent and the
request ID. Start admission remains atomic and lane IDs remain unique.

When a post-send timeout occurs, the CLI reads durable workspace state without starting another
supervisor. It compares every requested lane against persisted immutable admission fields: lane ID,
role, label, model, effort, checkout key, authority, and admission time after the request began.

- Exact match for every requested lane: return success with `admissionRecovered: true`, the persisted
  admission IDs, and a warning that the original response was lost.
- No matching lane: return runtime-unavailable with `requestSent: true`, `retrySafe: false`, and an
  instruction to run status rather than repeat start.
- Partial or conflicting match: return `outcome_unknown` admission evidence with `retrySafe: false`.

The CLI never converts an uncertain post-send timeout into an ordinary exit-4 failure with no JSON.
Machine JSON and human text carry the same retry-safety meaning.

## 3. Interrupted supervisor state

`interrupted` is a terminal attention state distinct from `failed` and `outcome_unknown`. Hydrating
an old `queued`, `starting`, or `running` record after supervisor loss produces `interrupted` unless
the runtime can prove a newer terminal Codex result. The record explains that execution state is
unknown and controller reconciliation is required.

Fleet does not attribute shared-checkout dirtiness to a single lane without evidence. It reports a
bounded workspace-level dirty/clean/unknown observation and preserves lane-specific evidence. The
controller decides whether to inspect the working tree, continue the existing thread, or retire the
lane. Automatic redispatch is forbidden.

## 4. Runtime authority and verification execution

Fleet builds one explicit app-server sandbox policy from admitted authority and applies it on thread
start, thread resume, and every turn start. Network access is never inferred from a role or prompt.
The mapping follows the current official app-server contract:

- Fleet `read-only` -> app-server `readOnly`.
- Fleet `workspace-write` -> app-server `workspaceWrite` with the admitted workspace as its writable
  root.
- Fleet `network: off` -> `networkAccess: false`.
- Fleet `network: live` -> `networkAccess: true`.

The first implementation spike probes app-server `command/exec` with exact argv in a disposable
workspace to determine whether a controller-owned build can run under the same sandbox on Windows.
The kill switch is any `EPERM`, sandbox denial, or inability to prove exact process ownership. If
refuted, Fleet does not use `process/spawn` as an unsandboxed workaround; it records a
`runtime_blocker` controller request containing the exact verification command and environment.

Lane prompts state four invariants: the admitted contract is execution authority; Fleet lanes do not
write Git metadata or claim controller commits; long/full suites must not consume the turn before
intermediate findings are saved; and PowerShell 5.1 commands run sequentially without `&&`. Build or
dev-server claims must reflect what actually ran. A controller-run build is separate evidence.

## 5. CLI status and result ergonomics

Status ordering is deterministic: `running`, `starting`, and `queued` first; then `blocked` lanes
whose phase is `needs-controller`, followed by `interrupted`, other `blocked`, `failed`, and
`outcome_unknown`; then successful terminal history. Ties use most recent activity and stable lane
ID.

Human status supports:

- `--all` for the complete bounded state list.
- `--limit <n>` for an explicit maximum.
- `--status <status>` for repeatable exact status filters.
- `--since <duration>` for bounded recent history.

Default human output remains bounded but reports shown/total counts and omitted counts by status.
Machine `--json` remains complete unless the caller explicitly supplies filters or a limit.

`result --pretty` emits indented JSON with a decoded structured `lastMessage` when it is valid JSON.
`result --summary` emits the lane verdict, work, verification, artifacts, config changes, controller
request, stop reason, interruption/reconciliation state, and diagnostics without nested escaped JSON.
The existing machine JSON shape remains available.

Status reads the Git branch with a bounded, read-only command. Runtime health probes only an existing
owned supervisor manifest; it never creates a supervisor. The result distinguishes ready,
unreachable, stale ownership, incompatible protocol, and not running.

## 6. Fleet Console navigation and responsiveness

The controller owns a lane viewport offset in addition to selected index. Wide and compact layouts
calculate visible lane capacity from terminal height and the two-line lane row. Moving selection,
PageUp/PageDown, Home/End, or mouse wheel updates both selection and viewport so the selected lane is
always rendered. The lane panel and signal line show `selected/total` and `visible-start–visible-end`.

Filtering applies before ordering and viewport calculation. Refresh preserves selection by lane ID
when possible, preventing jumps when active status changes.

Potentially blocking snapshot and supervisor operations receive bounded timeouts. The console keeps
rendering the last good snapshot with a visible stale/loading indicator and continues accepting
local navigation and quit input. A PTY stress test injects delayed reads, supervisor timeouts, resize,
mouse wheel, and rapid key input and proves terminal restoration and bounded responsiveness.

## 7. Documentation and operating guidance

The public and plugin documentation explain:

- `confirmationRef` binds the user's explicit approval to admitted mutable actions.
- Long or Turkish contracts should be saved as UTF-8 files and passed with `--contract`; shell
  argument splitting and console code pages are not trusted transport.
- Claude background tasks and Fleet Console are separate interfaces.
- Playwright's shared profile may reject parallel sessions; Fleet serializes one mutable browser
  operator and documents independent-browser fallback only when explicitly authorized.
- Stale MCP credentials are diagnosed as capability failures; Fleet does not silently replace the
  requested route.
- Marketplace plugin update and Ctrl+G integration-runtime upgrade are separate versioned steps.

Claims that depend on the real Codex account, Windows sandbox, Claude plugin cache, or GitHub release
are labelled with the exact environment and date of verification.

## 8. Version and dependency policy

The release version is `0.2.0`. All package, marketplace, plugin, broker, archive defaults,
documentation, and setup ownership metadata use that version.

The validated Claude Code CLI pin moves from `2.1.234` to `2.1.252` after local smoke and the full CI
matrix pass. The development dependency `node-pty` remains `1.1.0`, which is current at design time.
The imported `openai/codex-plugin-cc` source remains at upstream `v1.0.6` / commit
`db52e28f4d9ded852ab3942cea316258ae4ef346`, because upstream HEAD and latest tag still match those
exact values. The local Codex CLI is upgraded from `0.147.0` to current `0.151.0` and the live smoke
records the actual version used.

No production npm dependency is added. Current external APIs are verified against primary
documentation before implementation; guessed fields are forbidden.

## 9. Test and release gates

Production behavior follows RED -> observed failure -> minimal GREEN -> regression verification.
Each defect class receives a focused test before implementation, followed by sibling-pattern sweeps.

Required local gates:

1. Syntax/typecheck and all unit/integration tests.
2. Strict Claude plugin validation.
3. Secret, license, performance, and documentation checks.
4. Deterministic package and checksum/provenance verification.
5. Windows PTY stress and installed-launcher setup/upgrade/uninstall smoke.
6. Disposable real-account Codex smoke covering optional outcomes, controller request, network policy,
   timeout reconciliation where safely injectable, and independent verification.
7. Source, marketplace cache, and installed Ctrl+G runtime parity after line-ending normalization.

Production release flow:

1. Commit on a release branch with conventional English commit messages and no agent attribution.
2. Push the branch and open a pull request.
3. Require the full Windows, Linux x64/ARM64, and macOS Intel/Apple Silicon Node 22/24 CI matrix plus
   CodeQL/dependency gates applicable to the pull request.
4. Merge only when required checks are green.
5. Create and push `v0.2.0` only from the verified `main` commit.
6. Wait for the tag release workflow to rerun the full matrix and publish the GitHub Release assets.
7. Verify the remote release tag, zip, SHA-256 file, provenance JSON, and archive manifest.
8. Update the local Claude marketplace plugin and owned Ctrl+G runtime, restart/pick up the new
   version, and prove both report `0.2.0`.

Any red CI job, failed live smoke, version mismatch, dirty release source, unsafe command-execution
probe, or artifact digest mismatch blocks the production tag or release-complete claim.

## Residual boundaries

Fleet cannot guarantee model correctness, third-party browser profile concurrency, network service
availability, or that every project build is compatible with the Codex sandbox. It can guarantee
that these limitations are classified truthfully, surfaced to Claude with durable evidence, and not
silently converted into success, failure, or blind retry.
